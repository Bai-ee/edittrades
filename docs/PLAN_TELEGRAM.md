# T-1 — Telegram alerts + read commands (owner-approved 2026-09-24)

Status: plan; implementer starts on the orchestrator's go. Read-only toward the engine; never execution.
Goal: the owner's phone gets a Telegram message the moment a GOOD or SETUP appears, and can ask the engine the same questions the GPT answers, plus chart snapshots and journal logging. No GPT in the loop.

## Boundaries (hard)
- Never calls, imports or exposes `api/execute-trade.js`, `services/jupiterPerps.js`, `services/walletManager.js`, or any signing code. `TRADE_EXECUTION_ENABLED` stays untouched. No `/buy`, `/sell`, `/open`, `/close` commands exist.
- Only the owner's Telegram user id (env `TELEGRAM_ALLOWED_USER_IDS`) gets answers; everyone else gets silence.
- Secrets: `TELEGRAM_BOT_TOKEN` (Vercel env, set by the orchestrator), webhook secret `TELEGRAM_WEBHOOK_SECRET`. Never logged.
- Vercel Pro: functions cap lifted; cron every minute allowed. Still keep functions minimal.
- No engine rule/threshold change (two-week freeze). Journal writes go through the existing `POST /api/journal` handler code path (import the same append function), same record schema, `source: "telegram"`.

## Build
1. `api/telegram-webhook.js` (POST, verifies `X-Telegram-Bot-Api-Secret-Token`): parses commands, replies via Bot API `sendMessage` / `sendPhoto`. Commands: `/signals`, `/why <SYM>`, `/flags [SYM]`, `/wallet`, `/journal [n]`, `/status`, `/chart <SYM> <tf>`, `/log <text>`, `/help`, `/testalert`. Text formatting in Telegram MarkdownV2 or HTML, one metric per line, matching the GPT's FORMAT where sensible (GO IN / HOLD / NO TRADE + SETUP lines).
2. `api/telegram-cron.js` (GET, guarded by `CRON_SECRET` header from Vercel cron): every minute builds the compact context, compares to the last alert state in Blob `telegram/state.json` (per symbol: recommendation class, setup id, plan id/status, GOOD readiness), and sends: NEW GOOD (full plan levels, gross/net R, change condition, mark drift, tracker link), NEW SETUP (trigger sentence), GOOD → rejected/void, DATA_UNAVAILABLE/stale for > 5 min, mark unavailable for > 5 min. Dedup by ids; quiet hours env optional. Attaches the chart image for GOOD alerts.
3. `lib/telegram.js`: pure formatter (payload → messages) with tests; Bot API client with 5 s timeout; never throws to the cron.
4. `vercel.json` `crons`: `/api/telegram-cron` `* * * * *`. Routes for both functions.
5. Tracker page: "Alerts" row in Status (last alert time, alerts today, cron health), read from `telegram/state.json` via the manifest pattern the journal uses.
6. Docs: connector doc endpoint table (both functions, auth), CHANGELOG, DOCUMENTATION_INDEX, ARCHITECTURE_MAP (Delivery stage), test:archmap green.
7. Tests: `test-telegram.js` (formatter cases per class incl. SETUP; dedup logic; allowlist rejects; webhook secret rejects; no execution import; commands parse). MCP tests unchanged.

## Levels + quiet hours (owner spec 2026-09-24, notification-only)
Built in `lib/telegram.js` (`diffAlerts`, `parseAlertsArgs`, `inQuietHours`), `api/telegram-cron.js`, `api/telegram-webhook.js`; no engine, threshold, schema or config change; no new file or dependency.
- **Levels** in Blob `telegram/state.json` `prefs.level`: `good` (GOOD + GOOD ended), `setup` (adds SETUP; default), `watch` (adds new forming/triggering flag candidates). Data and mark health alerts always send. GOOD/SETUP detection and dedup are unchanged; a SETUP held back by level `good` is still remembered, so raising the level does not replay it.
- **Watch alerts**: once per new candidateId in state `forming` or `triggering` (never proto, failed, expired, confirmed); rolling memory of the last 200 ids (`state.watch.ids`); per-symbol cooldown 15 min (`state.watch.lastAt`). An alerted forming candidate that turns triggering passes the cooldown once. A candidate held back by the cooldown is not remembered, so it alerts when the cooldown ends if still live. One line, no chart: `WATCH · BTC 3m LONG forming · break 84,466.10 / void 84,331.60 · 2.4R · td:bull:3/4` (`TRIGGERING · …` for triggering; the td code is the symbol's top-down reason code, omitted when absent).
- **Quiet hours** in `prefs.quiet` (`{start, end}` hours, start inclusive, end exclusive, may wrap midnight; `null` = off): default 01:00–05:00 America/Chicago, every day. Clock via `Intl.DateTimeFormat('en-US', { timeZone: 'America/Chicago', hour: 'numeric', hourCycle: 'h23' })`, so DST is handled. Alerts inside the window send with `disable_notification: true`; nothing is dropped. The old UTC `TELEGRAM_QUIET_HOURS` env is no longer read.
- **Commands**: `/alerts` (show), `/alerts good|setup|watch`, `/alerts quiet HH-HH`, `/alerts quiet off`, `/alerts quiet` (show). Saved with the same ETag-guarded `updateBlob` the cron uses, so a concurrent cron run cannot lose the change. `/status` shows level and quiet window; `/help` lists the commands.
- **Tests** (`test:telegram` 41): level gating per class, watch dedup + cooldown + triggering pass-through + 200-id roll, quiet hours CDT/CST/weekend/wrap/off, `/alerts` parsing, prefs persistence through webhook and cron.

## Flags chart albums (owner spec 2026-09-24, notification-only)
- **Trigger**: `/flags [SYM]`, the `Flags` label, and the new `All flags` button under the Charts picker (`flags:all` → `/flags`).
- **Flow**: one full (non-compact) build; the existing text summary first (its compact view), then per symbol (BTC, ETH, SOL; `/flags SYM` limits to one) one album of every live flag via Bot API `sendMediaGroup` (multipart, `attach://photoN` parts, 5 s per request, ≤ 10 per group; a single image goes through `sendPhoto`, since groups need 2-10). Live = state `proto`, `forming`, `triggering`, `confirmed`, `expired`; `failed` excluded. One image per distinct symbol+timeframe; a long and a short on the same timeframe share it. A symbol without a live flag gets `BTC · no live flags`.
- **Caption** (HTML, ≤ 1,000 chars): one line per candidate on that timeframe, `BTC 3m · LONG forming · brk 84,466.10 · void 84,331.60 · 2.4R · qual watch (room:blocked-15m)` (up to 3 qual reasons), then `closed through HH:MM UTC`.
- **EMA lines**: the build's chart series hook serves one symbol+timeframe, so album charts rebuild EMA21/EMA200 over the published window backwards from the payload's last EMA value (`emaTailSeries`, presentation only).
- **Limits**: at most 9 images per call (symbol then timeframe order; a closing line names how many were cut). Charts render in parallel with a 6 s budget each; a failed or late chart (or a failed album send) goes out as its caption text plus `[chart unavailable]`. `api/telegram-webhook.js` exports `config.maxDuration = 60` (Pro) so build + renders + sends stay inside the function limit.
- **Tests** (`test:telegram` 49 → 55): collection + grouping, caption format and cap, media-group chunking + 9-image cap + EMA tail series, album order with `attach://` parts and the no-live line, render failure/timeout fallback, 9-cap limit line + `flags:all` button + allowlist + maxDuration.

## BREAKOUT alert + chase SETUP (owner priority 2026-09-24)
- **BREAKOUT** (cron, `diffAlerts`): once per candidateId when a candidate first reaches `confirmed` (per-symbol memory `symbols.<SYM>.breakoutIds`, last 50), sent at every alert level, before that symbol's SETUP. `BREAKOUT · BTC 5m LONG confirmed · brk 84,479.00 · void 84,349.70 · 3.9R · entry = retest of 84,479.00 that holds · plan rejected: chase` (the plan segment is the live plan's status/reason when it is this candidate's, else `plan: another candidate is selected`). Buttons Why / Chart / Took it / Skipped; the Took it snapshot uses the plan's levels, falling back to the candidate's breakout/invalidation/measured target.
- **Chase SETUP** (`lib/flagTradePlan.js`, copied through by `lib/flagRecommendation.js`): with no conditional attempt, a confirmed flag rejected only for `chase` whose re-attempt without the chase flag clears every other gate becomes `setup`, entryCondition `wait for a <tf> retest of <entry> that holds above|below it`. The live plan and class (BAD/chase) are unchanged, so the SETUP alert covers the retest once (dedup by candidateId, no per-candle repeat).
- **Tests**: `test:telegram` 55 → 58, `test:flagplan` 67 → 69, `test:flagrec:fixtures` 16 → 17.

## State versioning + health (incident fix 2026-09-24, delivery-only)
- **Incident**: a deploy changed the shape of Blob `telegram/state.json`; the cron returned 503 `state_write_Error` every minute for ~70 min and `/alerts` failed, with no alert to the owner. No engine change in the fix.
- **Versioning** (`lib/telegram.js` `migrateState` / `parseState`, `STATE_VERSION` = 2): never throws. A state without `stateVersion` is v1 and migrates forward: missing `prefs` → defaults (level `setup`, quiet 01–05 America/Chicago), missing or malformed memory (`goodIds`/`setupIds`/`breakoutIds`, `watch.ids`, `buttons`, marks) → empty, unknown fields kept. Unparseable JSON or a non-object → fresh default state, logged `reason=state_reset cause=unparseable|wrong_type`. Every write (cron diff, `/alerts`) stamps `stateVersion`; the cron writes a migrated or reset state on the first run. If the diff itself throws on a stored state, the cron starts over from defaults with the owner prefs kept (`cause=diff_error`).
- **Error text**: cron and webhook state failures log `reason=state_write_<name> msg="<err.message, first 200 chars>"` (`errText`: the bot token, cron secret, webhook secret, Blob token and token-shaped strings redacted). Never returned to a client or stored.
- **Health** (`telegram/health.json`, `nextCronHealth`): `{failures, since, lastReason, lastFailureAt, lastAlertAt, recoveredAt}`, written with `allowOverwrite: true` and no ETag, so a stuck state write cannot block it; a healthy run only reads it (no write). The 3rd consecutive failure sends `ALERTS CRON FAILING · <reason> · since <time>` to every allowed user, then at most once per hour while it keeps failing; the first success after ≥ 3 failures sends `ALERTS CRON RECOVERED` once. `/status` shows `Cron failures: N in a row · last failure: <reason> <time>`.
- **Tests**: `test:telegram` 58 → 64 (v1 migration gives the same alerts, corrupt/wrong-type reset, cron migrate + reset + `/alerts` on a reset state, health counter, FAILING on the 3rd then hourly, RECOVERED once, 503 log text redacted).

## Drill-down buttons, tracking, positions, timeframe focus, layout, /market (owner 2026-09-25, delivery-only)
Owner: "I need to be able to dig down into the trade… a button for anything I could think of to ask GPT." Built in `lib/telegram.js`, `api/telegram-webhook.js`, `api/telegram-cron.js`; no rule, threshold, schema or config change; no execution or signing import; no new dependency.
- **Buttons** on every WATCH, TRIGGERING, BREAKOUT, SETUP and GOOD alert and on each `/signals` symbol block with a flag: row 1 `Plan · Thesis · Chart`, row 2 `Track · Took it · Skipped` (`Untrack` once tracked; the tapped message's keyboard is swapped with `editMessageReplyMarkup`). callback_data ≤ 64 bytes: `plan:<ref>`, `thesis:<ref>`, `track:<ref>`, `untrack:<ref>`, `chart:SYM:TF`, `log:took|skip:SYM:<ref>` (ref = 8-hex FNV-1a of the candidateId). Every alert and `/signals` stores a candidate snapshot in `state.buttons` (last 50). A ref resolves against live data first (any candidate, plan, SETUP or WATCH candidate of any symbol), then the snapshot (`buttons`, then `tracked`); unknown (alerts sent before this deploy) → `[expired — send /signals]`.
- **Plan card**: `🧭 PLAN · <glyph> <b>SYM tf ▲ LONG</b>`, sections LEVELS (entry = retest level, stop, stop %, TP1, TP2 when present, R gross · net after direction cost), SIZING (from the candidate's `risk` block only: max / suggested leverage, collateral, size = suggested × collateral, loss at stop USD and % of wallet; else `Sizing: unavailable (<reason>)`), mark vs Kraken close with drift, TIMING (`Expect: ~n candles to TP1` only from a measured pathOutlook figure, else `n/a`; the candle timeframe; the path-history lean labeled an estimate), VERDICT (the alert's readiness call). A candidate without its own ready/conditional plan or SETUP carries `🔴 NOT A TRADE UNDER YOUR RULES — <short reason>` and still prints the levels on file; a missing target stays missing (a measured move is labeled a pattern projection).
- **Thesis card**: `🧠 THESIS · …`, the candidate's line (state, measured R, room R), counter-trend note, SUPPORTS ✔ / AGAINST ✖ / UNKNOWN ? from the symbol's flagRecommendation as short phrases (`reasonPhrase`, side-aware; unmapped code → the code), WHAT CHANGES THE CALL, TO BECOME GO IN (entryCondition, SETUP trigger, or the stage trigger). Lists shrink until the card fits 1,000 chars.
- **Track** (`state.tracked`, max 10, 6 h each; Took it implies Track and evicts the oldest untaken entry when full): reply `Tracking SOL 3m ▼ SHORT · brk 116.77 · alerts on every change`. The cron alerts every transition regardless of level or timeframe, at most one per candidate per run, and suppresses the generic alert for that candidate: state change (forming → triggering → confirmed), SETUP appears, plan READY (`GET IN NOW` with its chart and the Plan card as a follow-up), void (candidate failed or the Kraken close is through the invalidation), gone, expired, 6 h end. Once the plan is ready or Took it: TP1 / stop on the mark (Kraken close when the mark is not ok) with R at that price. Untaken → tracking ends. Taken → `Closed here` (journal `close`, exit = the hit price, resultR vs the logged entry/stop, linked by engineRef), `Partial` on TP1 (journal `adjust`, "partial at TP1"), `Still in` (no write, re-arms); one NUDGE 10 min after the hit when no close is journaled (the cron reads the journal only then and drops the nudge if a close exists). `/tracking` lists entries with Plan / Thesis / Untrack.
- **Positions**: `/positions` (menu `Positions`) = journal opens with no matching close (by engineRef.candidateId, else symbol + direction): entry, stop, TP1, live mark (else Kraken close), R now, R to stop and TP1, age; dot 🟢/🔴 by the R sign; buttons `Close @ mark` (`pclose:<ref>`, journal `close` at the mark with R) and `Chart`. Empty → `[NO OPEN TRADES]`. Journal kinds unchanged (open/close/adjust/skip/note), same `appendRecord` path, ids `tg_close_<ref>` / `tg_adjust_<ref>` so a double tap logs once.
- **Timeframe focus**: `prefs.alertTimeframes` (default `["3m","5m"]`, null = all) gates WATCH / TRIGGERING / BREAKOUT; `/alerts tf 5m | 3m,5m | all`, picker `3m+5m · 5m only · all` under Alerts; `/alerts` and `/status` show it. While a candidate is tracked, 1m flags of that SYMBOL + DIRECTION alert with line 0 `1m ENTRY · for your tracked SOL 5m ▼ SHORT` and the same buttons; opposite direction stays muted; ends when the entry leaves `tracked` (untrack, void, close, 6 h). GOOD, SETUP, tracked and health alerts are never filtered.
- **Layout** (HTML): line 1 `<dot> <glyph> <b>SYM tf ▲ LONG|▼ SHORT</b> · KIND` (🟢 GET IN NOW, 🟡 BE READY / WAIT, 🔴 STAND DOWN, ⚪ WATCH / status; ₿ BTC, Ξ ETH, ◎ SOL), then sections split by `────────────────`: LEVELS (`<code>` brk / void / meas / room, keys left, values right), VERDICT (bold call + plain reason), PLAN (only for the candidate's own plan or SETUP: entry / stop / stop dist / TP1 / TP2 / R gross·net / size · lev / loss$), CONTEXT (counter-trend or top-down, divergence, mark drift). Status is ⚪ with monospace key/values; health messages lead with 🔴/🟢. Cards stay under 1,000 chars.
- **/market** (menu `Market`): `🌐 MARKET · last 24h` from one bias build, engine fields only: per symbol price, 24h change and range (last 24 closed 1h candles; the payload publishes 20, so it falls back to the last 6 4h candles, labeled `(4h)`; neither → n/a), top-down `<sentiment> n/4`, 4h / 1h bias-matrix lean, EMA200 count, Stoch 15m / 1h (ob / os / neutral), mark drift; LEAN by rule (≥ 2 symbols top-down bull ≥ 3/4 → bullish structure, bear mirror, else mixed; ≥ 2 symbols Stoch overbought/oversold on 15m or 1h → stretched / bouncing / pulling back); FLAGS = alerts sent today by kind from `state.alerts.byKind` (formed = WATCH + TRIGGERING, confirmed = BREAKOUT, SETUP, GOOD; else n/a); WHAT WOULD CHANGE IT = the nearest 1h/4h support below (bull lean) or resistance above (bear), both for mixed.
- **Tests** (`test:telegram` 73 → 85): Plan card ready (short snapshot + long mirror), rejected (NOT A TRADE), no-risk and snapshot cases; Thesis phrases with no raw code across every emitted code; live-first / snapshot / expired refs; track lifecycle (tap, Untrack swap, triggering, SETUP, GET IN NOW + Plan card, void, gone, 6 h, max 10); TP1 / stop on mark and Kraken close, long + short, R at exit, nudge once; Closed here / Partial / Still in / Close @ mark records and `/positions`; nudge dropped when closed; timeframe focus and `/alerts tf`; `/market` render, bull and bear lean, n/a fields; ≤ 64-byte callback data; visual headers, arrows, rules and 1,000-char cap on every alert.

## Sent-alert and transition logs (owner 2026-09-25, logging only)
Makes alert timing and per-minute engine transitions part of the tracked record. No rule, threshold, schema or config change; no execution import; no new dependency. New `lib/telegramLog.js`; `api/telegram-cron.js` calls it after the sends.
- **Sent-alert log**: every alert the cron sends (alerts, tracked transitions, TP1/stop hits, nudges; not command replies, not the cron-health messages) appends one line to Blob `telegram/alerts/YYYY-MM-DD.jsonl` (UTC day of `sentAt`) + `telegram/alerts/manifest.json` (`telegram-alerts-manifest-1`) via `appendJsonlDay`: `{id, sentAt, kind, event, symbol, timeframe, direction, candidateId, signature, verdict, etaMin, breakout, invalidation, entry, stop, tp1, grossRR, netRR, roomR, closedThrough, silent, level, tracked, delivered, text}`. `id` = run time + index; `event` names a tracked transition (`state:<s>`, `setup`, `get_in_now`, `tp1`, `stop`, `void`, `gone`, `expired`, `ttl`, `nudge`); levels come from the live candidate, else the tracked entry; `verdict`/`etaMin` are parsed from the bold call; `text` = first 200 plain-text chars with the sizing rows (`size · lev`, `loss$`) cut. Never account, wallet or user fields; a row that fails the tracker's sensitive-key check or the credential check is refused.
- **Transition log**: `diffAlerts` keeps `state.cands` (`{candidateId: {sym, s, p}}` for every candidate the payload names) and returns `transitions` from `diffCandidates`: one line per candidate whose state or plan status changed since the previous run (new → `from: null`, dropped → `to: 'gone'`), appended to `telegram/transitions/YYYY-MM-DD.jsonl` + manifest: `{at, closedThrough, symbol, timeframe, direction, candidateId, from, to, planStatus, planFrom, reasonCode, class, breakout, invalidation, measuredRR}`. Nothing when nothing changed; unavailable data and a symbol missing from the payload write nothing; the first run after deploy seeds `cands` silently.
- **Best effort**: written after the sends, capped at 2 s, never throws; a failed log is logged as `logSkipped=<reason>` and never blocks or repeats a send. `TRACK_TELEGRAM_LOG=false` disables both. Cost: up to two extra guarded Blob writes per minute when something changed.
- **Tests** (`test:telegram` 85 → 90): alert line shape + strip check + sizing cut; tracked VOID keeps the tracked levels; transition diff (seed, state change, plan change, new, gone, unavailable, absent symbol); cron writes both day files + manifests once; failing log store never blocks a send; kill switch.
